# Scratch 경고등 — val 에서만 0.7835 인 이유, 착수 전 사전등록

작성 2026-08-23 15:50, 브랜치 `exp/ood-oneclass`. **한 줄도 실행하기 전에 쓴다.**
판정은 §7 에 append 한다.

## 1. 무엇을 묻는가

11차 사이클이 봉인 홀드아웃을 열고 **경고등 하나**를 남겼다.

| 파티션 | Scratch AUROC | n |
|---|---:|---:|
| `test_dev` | **0.9197** | 510 |
| `test_sealed` | **0.9414** | 183 |
| `val_unseen` | **0.7835** | **92** |

Scratch 는 이 워크스트림이 **가장 자랑한 클래스**다(0.6559 → 0.9251). 6차 사이클에서
정정 11(선 필터 분모)을 바로잡아 0.6332 → 0.9355 로 뒤집은 것이 이 워크스트림의 대표 사건이다.
**그 클래스가 다른 분포에서 흔들린 유일한 지점**이 여기다.

n<100 이라 사전등록 규칙대로 **판정에는 쓰지 않았고 이 사이클도 쓰지 않는다.**
그러나 **원인은 알아야 한다.** 세 가지 중 어느 것인지에 따라 대응이 완전히 다르다.

| 후보 | 무슨 뜻인가 | 대응 |
|---|---|---|
| **(a) 표본 잡음** | n=92 면 AUROC 이 원래 이만큼 흔들린다 | 아무것도 안 한다. 경고등을 끈다 |
| **(b) 음성 집합 이동** | val 정상이 더 더러워서 옅은 긁힘이 묻힌다 | 채점기 문제가 아니다. 정상 기준선이 문제다 |
| **(c) val Scratch 자체가 다르다** | 긁힘의 모양·굵기·길이가 다르다 | **진짜 약점이다.** 선 필터의 일반화 한계 |

## 2. 어떻게 가르는가 — 2x2 교차 분해가 핵심

클래스별 AUROC 은 **양성(그 클래스)과 음성(그 파티션의 정상)** 둘 다에 의존한다.
val 은 양성도 음성도 동시에 바뀌었으므로 **한 번에 재면 원인을 못 가른다.**
그래서 넷을 따로 잰다. 점수는 전부 **같은 채점기**(train-none 으로만 보정된 fuse3)로 낸다.

| | 음성 = dev 정상 | 음성 = val 정상 |
|---|---|---|
| **양성 = dev Scratch** | (1) 기준 = 0.9197 | (2) |
| **양성 = val Scratch** | (3) | (4) 관측된 0.7835 |

- **(3) 이 (1) 에 가까우면** 원인은 음성이다 → 후보 (b)
- **(2) 가 (4) 에 가까우면** 같은 결론이 강화된다 → 후보 (b)
- **(3) 도 낮으면** 원인은 val Scratch 자체다 → 후보 (c)

**두 파티션의 점수를 한 축에 놓고 비교할 수 있는 이유**: 보정 참조(백분위 ECDF, 반경 대역)가
**둘 다 train-none 하나**다. 평가 집합이 바뀌어도 채점 함수는 같다. 11차 사이클과 같은 규약이다.

## 3. 표본 잡음 귀무 — n=92 는 얼마나 흔들리는가

**dev Scratch 510장에서 92장을 비복원 추출해 AUROC 을 2,000번 잰다**(음성은 dev 정상 전부).
이것이 "같은 분포에서 n=92 로 재면 어떤 값이 나오는가" 의 귀무분포다.

- 그 분포의 **2.5 백분위가 0.7835 아래면** 관측값은 잡음으로 설명 가능하다 → 후보 (a)
- **위면** 잡음만으로는 설명이 안 된다

이걸 먼저 하는 이유: 여기서 끝나면 (b), (c) 를 따질 필요가 없다. 그리고 이 워크스트림은
**n=2 로 판정했다가 세 번 뒤집혔다.** n=92 를 그냥 믿지 않는다.

## 4. 요소별 분해 — 어느 신호가 무너지는가

fuse3 는 A(k2 5x5 + 반경보정), B(온전창 선 L=11), C(k2 3x3)의 융합이다.
넷 조합 각각에 대해 **fuse3 와 A, B, C 단독**을 따로 잰다.
**B 만 무너지면** "선 필터가 val 의 긁힘을 못 본다" 는 구체적 주장이 되고, 그건 후보 (c) 다.

## 5. 형태 통계 — dev Scratch 와 val Scratch 가 실제로 다른가

**라벨을 표본 선택에만 쓴다. 어떤 점수 계산에도 안 들어간다(범위 C 위반 아님).**
이 통계는 **기술 통계이며 arm 을 고치거나 고르는 데 쓰지 않는다.**

웨이퍼마다 잰다.

| 통계 | 왜 |
|---|---|
| `die_size` | val 전체 중앙값이 845 로 dev 533 보다 크다. 긁힘도 그런가 |
| 불량 다이 개수 / 비율 | 양의 축 |
| 최대 연결성분 크기(8-이웃) | 긁힘이 이어져 있는가 |
| **불량 다이의 평균 불량 이웃 수** | **굵기 대리.** 굵은 선일수록 이웃이 많다 |
| 최대 연결성분의 **이심률**(관성 텐서 고윳값 비) | **가늘고 긴가.** 긁힘의 정의에 가깝다 |
| 최대 연결성분의 주축 길이 | 긁힘 길이 |

dev Scratch 와 val Scratch 의 이 여섯 분포를 중앙값과 Mann-Whitney U 로 비교한다.

## 6. 봉인 규약 — 11차 사이클의 자진 신고에 대한 응답

11차 사이클이 **R5(파티션당 딱 한 번)를 어겼다고 자진 신고**하고
"다음 사전등록에는 사후 기술 통계를 몇 번까지 허용하는지 따로 적으라" 고 남겼다. 그대로 한다.

1. **`val_unseen` 해제는 이 사이클에서 정확히 1회다.** 한 프로세스 안에서 한 번 로드하고
   그 안에서 §2~§5 를 전부 끝낸다. 스크립트를 나누지 않는다.
2. **`test_sealed` 는 열지 않는다.** 이 사이클에 필요 없다.
3. **이 사이클은 val 로 어떤 arm 도 고르거나 기각하거나 튜닝하지 않는다.**
   산출물은 **원인 진단 하나**이고, 채택 표를 건드리지 않는다.
4. 결과가 후보 (c) 로 나와도 **여기서 선 필터를 고치지 않는다.** 고치면 val 에 적합시키는 것이다.
   고칠 값어치가 있다는 것만 기록하고, 실제 수정은 **dev 에서** 사전등록해 한다.

## 7. 반증 조건과 판정 규칙 (실행 전에 박는다)

- **S1.** dev 부표집 귀무의 2.5 백분위 <= 0.7835 → **후보 (a) 로 판정.** 경고등을 끈다.
- **S2.** S1 이 아니고 (3) 이 (1) 의 부표집 귀무 95% 구간 안 → **후보 (b).**
- **S3.** S1 이 아니고 (3) 이 그 구간 아래 → **후보 (c).** 형태 통계에서 무엇이 다른지 보고한다.
- **S4.** 형태 통계 여섯 개 중 **Bonferroni 보정(alpha=0.05/6=0.0083)** 을 통과하는 것만
  "다르다" 고 적는다. 나머지는 "차이를 못 봤다" 로 적는다.
- **S5.** 어떤 경우에도 **`docs/reports/OOD.md` 의 채택 수치는 안 바꾼다.**

## 8. 실행 전 예측 — 실행 후 채점한다

1. **dev 부표집 귀무의 2.5 백분위가 0.7835 아래다** → 잡음으로 설명 가능(후보 a).
   근거: AUROC 표준오차는 대략 n^-0.5 로 커지고 510 → 92 는 2.4배다.
2. 그래도 (3) 은 (1) 보다 **낮게** 나온다(방향은 실재하고 크기가 과장됐다).

4. val Scratch 의 `die_size` 중앙값이 dev Scratch 보다 **크다**(val 전체가 845 대 533).

6. **굵기 대리(평균 불량 이웃 수)는 차이가 안 보인다** — 즉 후보 (c) 의 구체적 기작을 못 찾는다.

| 4 | val Scratch 의 die_size 가 더 크다 | 맞음 (904 → 2,393). 다만 **원인은 아니었다** |
| 5 | val Scratch 의 불량 비율이 비슷하거나 낮다 | 맞음 (0.103 → 0.051) |
| 6 | 굵기 대리는 차이가 안 보인다 | **틀림.** p=2.7e-03 으로 다르고 **이게 핵심 축이었다** |

**1과 6이 같은 뿌리다 — 나는 이 경고등이 표본 잡음이길 기대했고, 그래서
"기작을 못 찾을 것" 이라고 예측했다.** 둘 다 틀렸다.

### 결론 — 진짜 약점이다

1. **Scratch 경고등은 실재한다.** n=92 의 잡음이 아니다(귀무 2,000회 중 0회).
2. **기작은 크기가 아니라 굵기와 이심률이다.** 가늘고 긴 긁힘일수록 점수가 낮고,
   그것을 좋아하는 요소는 **선 필터 하나뿐**이며 융합에서 A, C 에 2대 1로 눌린다.
3. **동시에 val 의 정상은 더 뭉쳐 있어** 양쪽에서 간격이 좁혀진다.
4. **큰 웨이퍼(`>1600`) 위의 긁힘을 이 워크스트림은 6장밖에 본 적이 없다.**

### 이것으로 무엇을 하지 않았는가

- **선 필터를 고치지 않았다.** 고치면 val 에 적합시키는 것이다(§6-4).
- **채택 arm 을 바꾸지 않았다.**
- **val 을 다시 열지 않았다.**

### 다음에 할 것 — dev 에서 사전등록해서

**요소 가중을 test 로 고르지 않는다는 규약**(현재 동일 가중 Fisher)이 여기서 비용을 낳는다.
가는 긁힘에서 B 만 옳고 A, C 가 틀리는데 셋을 똑같이 센다.
**정상 데이터만으로 가중을 정하는 방법**(예: 요소별 train-none 분산으로 표준화, 또는
요소 간 상관을 train-none 에서 재서 백색화)이 범위 A 안에 있고, 그러면 test 로 안 고른다.
**이것을 다음 사이클의 주 arm 으로 사전등록할 값어치가 있다.**

# 3단계 준비 — 국소화 맵이 하류 분류를 돕는가, 착수 전 사전등록

작성 2026-08-23 16:2x, 브랜치 `exp/ood-oneclass`.
**MLLM 을 한 번도 호출하기 전에 쓴다.** 판정은 §11 에 append 한다.

## 1. 무엇을 묻는가

파이프라인은 `OOD 탐지 → 다이 단위 국소화 → MLLM 8종 분류 → 유저 질의응답` 이다
(기획서 §9). 1단계는 끝났고 2단계 산출물(맵)도 나와 있다.
`result/ood/o1_pipeline_maps/pipeline_maps_pad.npz` 에 12,894장이
**세 요소 맵 + 원본 + 융합 점수**로 저장돼 있다.

**그런데 그 맵이 하류에 값어치가 있는지는 한 번도 재지 않았다.**
국소화에는 픽셀 정답이 없으므로(기획서 §9.3, 만들지 않는다) **직접 평가가 불가능**하다.
그래서 §9.4 대로 **간접 평가**를 한다.

> **맵을 같이 주면 8종 분류가 더 잘 되는가.**

## 2. 실행 전에 못 박는 결정적 사실 — 맵은 정보를 더하지 않는다

**세 요소 맵은 원본 웨이퍼맵의 결정론적 함수다.** A, B, C 전부 원본에서 계산된다
(반경 대역 참조만 train-none 에서 왔고 그것도 고정된 상수 테이블이다).
그러므로 **정보 이론적으로 맵은 원본에 아무것도 더하지 않는다.**

이걸 §1 에 안 적으면 나중에 "맵이 정보를 더한다" 로 결과를 잘못 읽게 된다.
여기서 묻는 것은 정확히 이것이다.

> **이미 다 들어 있는 정보를 미리 계산해 보여 주는 것이 읽는 쪽에 도움이 되는가.**

그건 실증적 질문이고 답이 "아니오" 일 수 있다. 그 경우 **맵은 사람이 보는 설명용이지
기계가 읽는 특징이 아니다** 가 결론이고, 그것도 결과다.

## 3. 이 감사가 이미 알려 준 것 — 탐지 최선이 분류 최선이 아니다

`candidate/ood_class_information.md`(8차 사이클, `result/ood/o1_classinfo/`):

| 신호 | 28쌍 중 1위 횟수 |
|---|---:|
| **자명한 불량 다이 개수** | **18** |
| 융합 fuse3 | 13 |

**탐지에서 압도적인 융합이 클래스 판별에서는 개수한테 진다.**
다만 특정 쌍에서는 파생 특징이 크게 이긴다 — **Scratch 대 Center 는
개수 0.599 인데 `log(B)-log(C)` 가 0.909** 다.

→ **넘길 것이 정해져 있다: 불량 다이 개수 + 세 요소 맵 + 파생 `log(B)-log(C)`.**
어느 하나가 지배하지 않으므로 넷을 다 넘기고, **무엇이 실제로 기여하는지를 arm 으로 가른다.**

## 4. arm 설계 — 위약과 스칼라 대조가 핵심이다

이 워크스트림의 정정 12건 중 여러 건이 **빠진 대조군**에서 나왔다(정정 2, 9, 12).
"맵을 넣으니 올랐다" 는 관측은 최소 세 가지로 설명된다. 넷을 다 만들어 가른다.

| arm | 프롬프트에 무엇이 들어가나 | 이미지 수 |
|---|---|---:|
| **C0 (대조)** | 원본 웨이퍼맵 1장 + 8종 이름·텍스트 설명 | 1 |
| **E1 (실험)** | 원본 1장 + **그 웨이퍼의** 세 요소 맵 3장 + 스칼라 2개 | 4 |
| **P1 (위약)** | 원본 1장 + **무작위로 짝지은 다른 웨이퍼의** 요소 맵 3장 + 그 웨이퍼의 스칼라 2개 | 4 |
| **S1 (스칼라만)** | 원본 1장 + **그 웨이퍼의** 스칼라 2개 (맵 이미지 없음) | 1 |

세 차이가 각각 다른 것을 잰다.

- **E1 − P1 = 맵 내용의 기여.** 이미지 개수와 토큰 수가 같으므로
  "그림을 더 주면 그냥 잘한다" 를 뺀다. **이 대조가 없으면 판정이 무효다.**
- **E1 − S1 = 맵 이미지가 스칼라 위에 더하는 것.** 여기가 0 이면 맵 이미지를 안 넘긴다
  (스칼라 두 개가 훨씬 싸다).
- **S1 − C0 = 스칼라만의 기여.** §3 의 감사가 이게 클 것이라 예고한다.

**(탐색) M1 = 맵 3장만, 원본 없음.** 맵이 원본을 대체할 수 있는지. 주 arm 이 아니다.

## 5. 맵을 어떻게 그릴 것인가 — 렌더링도 실행 전에 못 박는다

정정 11 의 교훈은 "코드보다 먼저 정하라" 였다. 렌더링에는 자유도가 많고
그 자유도를 결과 보고 고치면 그건 튜닝이다.

1. **척도는 train-none 에서 고정한다.** 요소별로 train-none 다이 값의
   1/99 백분위를 [0,1] 로 잡고 자른다. **test 통계를 안 쓴다**(범위 A 유지).
2. **웨이퍼 밖은 순수 검정**, 다이는 색상표. 색상표는 요소 셋 다 같은 것을 쓴다.
3. **해상도는 64x64 를 최근접 이웃으로 8배 확대**(512x512). 보간하면 격자 구조가 뭉개지는데
   이 데이터는 명목형 격자다(기획서 §7, 임의 각도 회전 금지와 같은 이유).
4. **원본은 3색 명목 색상표**(다이없음/정상/불량). 연속 색상표를 쓰지 않는다.
5. **네 이미지의 순서는 고정**: 원본, A, B, C. 반복마다 순서를 바꾸지 않는다
   (순서 효과는 §8 의 반복이 아니라 별도 탐색 arm 에서 잰다).

## 6. 평가 집합 — 봉인 규약을 지킨다

**맵 npz 는 봉인 이전에 만들어졌다.** 12,894장 중 **9,509장이 `test_dev`,
3,385장이 봉인**이다(실측). 그러므로:

1. **개발은 `test_dev` 안의 9,509장에서만 한다.** `cache_index` 를 `load_partition("test_dev")`
   와 교집합해 거른다. 봉인 3,385장은 만지지 않는다.
2. 그 안의 결함 클래스별 장수(실측): Center 618, Donut 103, Edge-Loc 2,000,
   Edge-Ring 856, Loc 1,451, Random 184, **Scratch 517, Near-full 70**.
3. **주 평가 집합 = 클래스당 70장씩 균형 표본 560장.** 최소 클래스(Near-full 70)에 맞춘다.
   macro-F1 은 작은 클래스가 지배하므로 균형이 맞아야 분산이 작다.
   표본은 **고정 시드로 한 번 뽑고 네 arm 에 똑같이 쓴다**(짝지은 비교).
4. **부 평가 집합 = 자연 유병률의 dev 결함 전체 5,799장** — 예산이 되면.
   주 판정은 3번으로 한다.

## 7. 지표

- **주 지표 = 8종 macro-F1** (결함 8종만. `none` 은 1단계가 이미 걸렀다는 전제)
- 병기: 클래스별 F1, 혼동 행렬, **`Scratch|Center` 쌍 정확도**(§3 이 지목한 곳),
  무응답·형식 위반 비율
- **형식 위반과 거부는 오답으로 센다.** 빼고 세면 arm 마다 다른 집합을 재게 된다
- 짝지은 비교: 같은 560장에 대해 웨이퍼 단위 부트스트랩으로 macro-F1 차이의 95% CI

## 8. 확률성 — 최소 3 반복

이 프로젝트는 **n=2 로 판정했다가 세 번 뒤집혔다**(기획서 §6-4).

- temperature 0 으로 고정하되 **그래도 3회 반복**한다(디코딩이 완전 결정론적이라는 보장이 없다)
- **3 반복의 최소값**이 대조군의 최대값을 못 넘으면 채택하지 않는다
- 반복 간 변동을 이득과 나란히 보고한다. **변동이 이득보다 크면 무승부로 적는다**

## 9. 범위 선언 — 어디까지가 one-class 인가 (기획서 §10)

| 무엇 | 범위 |
|---|---|
| 요소 맵 A, B, C 와 스칼라 | **A** (정상만으로 만들어졌다) |
| 프롬프트에 8종 **이름과 텍스트 설명**을 쓰는 것 | **B** (결함 모양 사전지식) |
| 프롬프트에 **실제 결함 표본 이미지**를 few-shot 으로 넣는 것 | **C — 금지** |
| 결함 라벨로 분류기를 학습·미세조정하는 것 | **C — 금지** |

**3단계는 필연적으로 B 다.** "8종 중 무엇인가" 라는 질문 자체가 8종을 열거하기 때문이다.
그러므로 1단계의 "결함 유형을 미리 열거할 수 없다" 는 전제는 **3단계에 적용되지 않는다.**
보고할 때 1단계 수치와 3단계 수치를 **섞지 않는다.**

### 9.1 정직하게 적어야 할 오염 — MLLM 은 이미 WM-811K 를 봤을 수 있다

WM-811K 는 널리 쓰이는 공개 데이터셋이다. **어떤 MLLM 이든 사전학습에서
이 데이터셋의 이미지와 라벨을 봤을 가능성이 있고, 우리는 그것을 확인할 수 없다**
(이 세션은 웹 검색이 소진됐고, 어차피 학습 자료 목록은 공개돼 있지 않다).

그러므로:

1. **zero-shot 점수를 "결함 라벨을 한 장도 안 썼다" 의 증거로 쓰지 않는다.**
   우리가 안 썼을 뿐 모델은 썼을 수 있다.
2. 지도학습 9-class macro-F1 0.790 과의 최종 비교(기획서 §9.6)는
   **이 오염을 명시한 채로만** 인용한다.
3. **그러나 이 사이클의 주 판정은 오염에 영향받지 않는다** —
   네 arm 이 같은 모델·같은 오염을 공유하므로 **arm 간 차이**는 여전히 유효하다.
   이것이 대조군을 넷으로 만든 또 하나의 이유다.

## 10. 반증 조건 — 하나라도 걸리면 그 결론을 적는다

1. **E1 − C0 의 짝지은 CI 하한 <= 0** → 맵 묶음이 하류를 돕지 않는다. **넘기지 않는다.**
2. **E1 − P1 의 CI 가 0 을 포함** → 이득은 맵 **내용**이 아니라 **이미지 개수/토큰**에서 왔다.
   **이 경우 1번을 통과해도 채택하지 않는다.**
3. **E1 − S1 의 CI 가 0 을 포함** → 맵 **이미지**는 불필요하다. **스칼라 두 개만 넘긴다.**
4. **클래스별 F1 이 하나라도 CI 가 겹치지 않게 내려가면 채택 보류**(기획서 §6-2).
   평균만 오르는 개선은 채택하지 않는다.
5. **3 반복 최소값이 대조군 최대값 아래면 기각**(§8).
6. **결함 표본 이미지를 프롬프트에 넣었으면 전체 무효**(§9, 범위 C).
7. **봉인 3,385장을 만졌으면 전체 무효**(§6-1).

## 11. 검정력을 실행 전에 적어 둔다 — 무엇을 못 잴 것인가

주 집합 560장, 클래스당 70장. 짝지은 웨이퍼 단위 부트스트랩이라 arm 간 공통 분산이 빠진다.
그래도 **클래스당 70장이면 클래스별 F1 의 해상도가 거칠다**(오답 한 장이 약 0.01).

**대략 macro-F1 차이 0.05 이상은 가릴 수 있고 0.02 이하는 못 가린다고 본다.**
그러므로 **"차이가 없었다" 는 "0.02 보다 작았다" 로만 읽는다.**
이 문장을 실행 전에 적어 두는 이유는, 결과가 무승부일 때
"검정력이 모자랐다" 를 사후에 꺼내 쓰지 않기 위해서다.

## 12. 실행 전 예측 — 실행 후 채점한다

1. **S1 − C0 > 0 이다.** 스칼라(불량 다이 개수)가 §3 에서 28쌍 중 18에서 1위였다.
2. **E1 − S1 의 CI 가 0 을 포함한다.** 즉 **맵 이미지는 스칼라 위에 못 보탠다.**
   맵은 원본의 결정론적 함수이고, MLLM 은 이미지에서 세밀한 수치를 잘 못 읽는다.
3. **E1 − P1 > 0 이다** (위약보다는 낫다). 틀린 맵은 적극적으로 해롭다.
4. **Scratch 와 Center 를 가르는 데서만 맵이 눈에 띄게 돕는다** — §3 이 그 쌍을 지목했다.
5. **어떤 arm 도 지도학습 macro-F1 0.790 근처에 못 간다.** 8종 zero-shot 은 훨씬 낮을 것이다.

**예측 2 가 맞으면 3단계에 넘길 것은 맵이 아니라 스칼라 두 개이고,
맵은 "사람이 보는 설명" 으로만 남는다.** 그것이 가장 값어치 있는 결과일 수 있다 —
파이프라인이 훨씬 싸진다.

## 13. 이 세션에서 못 하는 것 — 정직하게

**이 사이클에서 MLLM 을 호출하지 않았다.** 이 워크스트림에는 MLLM 접근 경로가 붙어 있지 않고,
웹 검색도 소진됐다. **그래서 이 문서는 설계이고 판정이 아니다.**

다음 세션이 바로 실행할 수 있도록 남겨 둔 것:

- arm 넷의 프롬프트 구성(§4)과 렌더링 규약(§5) — 자유도를 다 못 박았다
- 평가 집합의 정확한 크기와 봉인 교집합(§6, 실측)
- 반증 조건 7개(§10)와 검정력 한계(§11)
- 실행 전 예측 5개(§12)

**아직 안 한 것**: 렌더링 코드, 프롬프트 문자열 확정, 응답 파싱 규약,
어떤 모델을 쓸지. 모델을 고르는 순간 §9.1 의 오염 논의를 그 모델에 맞춰 다시 적어야 한다.

# 입력 해상도 — 정보량 축은 닫혀 있다

**결론: 해상도를 올려도 새 정보가 없다.** test 118,595장 중 원본이 64를 넘는 것은
**325장(0.3%)** 뿐이고, **96을 넘는 것은 0장**이다. 재현:
`python3 src/diag_native_resolution.py` (학습 없음, 원자료
[evidence/native_resolution.json](evidence/native_resolution.json)).

## 무엇을 물었나

Scratch(F1 0.710)는 가는 선이라 64x64 가 그것을 뭉갤 수 있다는 가설이 있었다.
반론은 "원본이 대부분 26x26 대라 상향 리사이즈가 정보를 만들지 못한다" 였다.
**둘 다 참일 수 있으므로 갈리는 지점을 찾아야 했다.**

`a1_preprocess.pad_center` 는 원본이 목표 크기보다 클 때만 nearest 로 **줄인다.**
그 웨이퍼들만이 해상도로 정보를 잃는다. 나머지는 여백에 놓일 뿐이라
96 으로 키워도 없던 셀이 생기지 않는다. 그래서 물어야 할 것은 하나다 —
**test 의 몇 %가 실제로 축소를 겪는가.**

## 답

| | 값 |
|---|---:|
| test n | 118,595 |
| 원본 H, W 중앙값 | **34 x 34** |
| 최빈 크기 | 30x34(12,291), 29x26(11,708), 39x37(10,104), 33x29(8,062), 26x26(7,997) |
| **64 를 넘는 웨이퍼** | **325장 (0.3%)** |
| **96 을 넘는 웨이퍼** | **0장 (0.0%)** |

축소되는 325장에서는 실제로 크게 잃는다 — 남는 다이 비율 중앙값 0.806,
하위 10% 는 0.510. 총 1,437,206개 중 547,463개(38%)가 사라진다.
**그러나 그것은 test 의 0.3% 다.**

클래스별로도 병목과 겹치지 않는다.

| 클래스 | support | >64 비율 | H 중앙값 | W 중앙값 |
|---|---:|---:|---:|---:|
| none | 110,701 | 0.3% | 33 | 34 |
| Edge-Loc | 2,772 | **0.1%** | 35 | 34 |
| Loc | 1,973 | 0.6% | 33 | 33 |
| Edge-Ring | 1,126 | 0.1% | 38 | 36 |
| Center | 832 | 0.5% | 34 | 34 |
| **Scratch** | 693 | **1.0%** (7장) | 34 | 34 |
| Random | 257 | 0.0% | 34 | 34 |
| Donut | 146 | 2.7% (4장) | 35 | 31 |
| Near-full | 95 | 0.0% | 33 | 29 |

병목인 Edge-Loc 은 **0.1%(4장)** 로 가장 낮다. Scratch 는 1.0% 로 가장 높지만
693장 중 **7장**이다. 7장으로 F1 0.710 을 설명할 수 없다.

## 따라온 정정 — `resize 96` 이 준 것은 정보가 아니다

이 보고서는 `e8_res96` 이 단독 +0.005(잡음의 1/10)인데 앙상블에는 기여한다(LOO +0.0044)고
적어 왔고, 그것을 "표현 다양성" 으로 설명했다. **표현 다양성이라는 결론은 그대로 맞지만
그 안의 메커니즘 하나가 배제된다 — 정보량은 아니다.**

96 을 넘는 test 웨이퍼가 0장이므로 `resize 96` 은 **모든** 웨이퍼를 확대한다.
nearest 확대는 셀을 복제할 뿐 없던 셀을 만들지 못한다. 그러므로
pad64, resize64, resize96 세 표현이 **담고 있는 정보는 사실상 같다.**

세 표현이 실제로 다른 것은 **웨이퍼가 conv 수용영역 대비 몇 배 크기로 놓이는가** 다.

| 표현 | 34x34 웨이퍼가 캔버스에서 차지하는 크기 | 배율 |
|---|---|---:|
| pad64 | 34x34 (원본 그대로, 나머지는 여백) | 1.0x |
| resize64 | 64x64 (캔버스를 채움) | 1.9x |
| resize96 | 96x96 | 2.8x |

**표현 다양성은 척도 다양성이었다.** 같은 정보를 서로 다른 배율로 놓으면
고정된 3x3 커널이 물리적으로 다른 범위를 본다.

이것은 E20(국소 밀도 채널)과 정확히 같은 이야기다 — k=3 이 무의미하고
k=5, k=7 에서만 신호가 나는 것도 "커널이 다이 몇 개를 덮는가" 의 문제였다.

## 그래서 무엇을 할 것인가

- **해상도를 체계적으로 훑을 값어치가 없다.** 96 위로는 정보가 0 이고,
  64 아래로 내려가면 0.3% 를 제외한 전부에서 정보를 **잃기** 시작한다.
- 대신 **척도**를 다양성 축으로 쓰는 것은 값어치가 있을 수 있다.
  resize128, resize32 는 정보를 바꾸지 않고 배율만 바꾼다.
  **아직 안 해봤다.** 이번 사이클에는 시간이 없었다.
- 다만 척도는 이미 세 값(1.0x, 1.9x, 2.8x)이 풀에 있고, 앙상블은
  구성원을 더 넣는다고 오르지 않았다(38개 < 18개). 기대는 낮게 잡는다.

## 재현

```bash
python3 src/diag_native_resolution.py
```
원본 `data/wm811k/LSWMD.pkl` 을 읽어 test 웨이퍼의 원본 (H,W) 를 세고,
`pad_center` 와 같은 축소를 걸었을 때 남는 다이 수를 센다. GPU 를 쓰지 않는다.

## 정정 — train 은 다르다. 위 결론은 test 에 대한 것이다

위 표는 test 만 봤다. 세 분할을 전부 세니 **train 과 test 가 크게 다르다.**

| 분할 | n | H, W 중앙값 | >64 | >96 | 최대 |
|---|---:|---:|---:|---:|---|
| train | 43,223 | **27 x 27** | 2,498 (5.78%) | 830 (1.92%) | **212 x 204** |
| val | 11,132 | 27 x 27 | 658 (5.91%) | 234 (2.10%) | 212 x 175 |
| **test** | 118,595 | **34 x 34** | 325 (0.27%) | **0 (0.00%)** | **86 x 89** |

두 가지를 고쳐야 한다.

1. **"96 을 넘는 웨이퍼가 0장" 은 test 에만 참이다.** train 에는 830장(1.92%) 있고
   그것들은 `resize 96` 에서도 축소된다. 다만 `resize 64` 에서 더 크게 축소되므로,
   **train 쪽에서는 96 이 64 보다 정보를 더 담는 것이 맞다.**
   그래도 **test 성능에 쓸 수 있는 추가 정보는 여전히 0** 이다 — test 는 전부 96 이하다.
2. **분할 간 크기 이동이 하나 더 있다.** train 중앙값 27x27, test 34x34 이고
   최대는 212x204 대 86x89 다. `splits.md` 가 기록한 none 비율 이동(67.6% -> 93.3%)에
   더해 **크기 분포도 다르다.** 극좌표(E15b)가 무너진 이유와 같은 계열의 이동이고,
   E17 의 `scale` 증강이 노렸던 갭도 이것이다(그리고 안 통했다).

**"해상도 축은 닫혀 있다" 는 결론 자체는 유지된다** — 판정은 test 에서 쓸 수 있는
정보량으로 하는 것이고 그것은 96 위에서 정확히 0 이다.
